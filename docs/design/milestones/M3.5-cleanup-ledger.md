**Confirmed fixed:**
- **C-4 fixture == README** (verified: `order-status` Pending/Shipped(tracking string)/
  Cancelled(reason string); `describe :returns string` with `(++ …)` branches). String
  literals synth `String`; EETF encodes `String` as an Erlang **char list** (`encode_string`,
  distinct from `encode_binary`), so `++` works at runtime; `++ → List`, `String <: List`
  ⇒ the README example **type-checks and runs**. The stand-in is gone.
- **C-1** render snapshot is a genuine exact `assert_eq!` of the full span+caret human
  output (`error[E001] … --> greeting.tlfe:3:1 … ^`) + JSON. Done.
- **C-5** honestly `deferred` (cfg-test, re-entry noted). Good.

**NEW finding requiring correction (correctness/soundness):**
- **The string↔binary conflation survives in `types_compatible`.** Lines map
  `(Binary, String)` and `(String, Binary)` as **compatible** — but in LFE a binary
  (`#"…"`) is NOT a char-list string (`"…"`); they're distinct runtime types (`++` works on
  strings/lists, not binaries). So a `:returns string` body returning a binary (or a binary
  where a string is expected) wrongly passes — a soundness hole, and exactly the residue of
  the looping. CC fixed the *literal* but not the *relation*. **Fix:** remove both
  `Binary⇄String` arms (keep `String⇄List`; `Binary` stands alone). Add a rejection test:
  a `:returns string` returning a binary value is REJECTED (exact diagnostic). Verify no
  existing test depended on the wrong rule (if one did, that test asserted the wrong thing).
  → **C-4 reopened** (the string-typing claim is incomplete until this lands).
- *(Secondary, note-only:)* `(List, String)` compat is over-loose (a general list isn't
  always a string); acceptable as gradual for now, revisit if it bites. Binary literals
  `#"…"` are not lexed yet (known gap; rides the bit-syntax deferral).
