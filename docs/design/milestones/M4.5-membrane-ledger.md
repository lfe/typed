## What Worked

- **match-lambda validators** compile cleanly through `lfe_codegen` — the same
  pattern that works for guarded function heads works for validator dispatch.
- **Reconstructing the tuple** in the ok-case from bound fields (not bare `term`)
  was the key fix that made validators actually compile.
- **The duality test** (D-4) is the most satisfying: same bad value `42`, two
  behaviors — `describe(42)` crashes, `decode-order-status(42)` returns error.
  This is exactly the design intent: guards for internal contracts (let-it-crash),
  validators for external input (graceful).
- **`decode` = `validate` + empty path** is a clean composition — no separate
  implementation needed.

## CDC Verification

**Verifier:** Claude (CDC), 2026-06-07, against `5cd4cad` / `ff145a4`. **Method:** static
inspection of `validators.rs` + the runtime CT suite.

**Genuinely done (verified) — credit the hard part:**
- **D-4 duality + D-3 graceful decode.** `decode-order-status(42)` → `#(error #(type_error
  …))` (no crash); `describe(42)` raises (crash). Same value, two behaviors — the membrane's
  graceful-return vs. let-it-crash distinction is real and tested. This is the conceptually
  hardest, most satisfying part.
- **D-8** regression/process: 34/34 CT, 63/63 Rust, `make check` clean.
- The validator *code* (`validators.rs`) does generate field-type checks (`make_field_checks`)
  and a `path` (`++ path (list 'field)`) — the deep machinery exists.

**Finding (cluster) — the DEEP capability is implemented but UNTESTED, and it's the whole
point of M4.5:** every CT test exercises only top-level cases — `decode(pending)` (a
*nullary* ctor, zero fields), `decode(42)` and the duality's `42` (top-level non-matches),
`{bogus,1}` (wrong tag). **None** validates a constructor *with fields*, none exercises a
**bad field** (`{shipped, 42}` where `tracking` is binary), every error has **`path: []`**,
and **enum/transparent** validators have no CT at all. So the field-type checking,
path-at-depth, nesting, and non-tagged-tuple backends — exactly what distinguishes M4.5's
*deep* validators from M4's *shallow* guards — have **zero coverage**; the tested invalid
cases are ones M4's guard already catches. Per the standing rules (test the criterion's
actual subject; untested capability ≠ `done`), these are reopened:
- **D-1 → open:** add a with-fields valid (`{shipped,<<"TRK">>}`→`#(ok …)`) + **bad-field**
  invalid (`{shipped,42}`→`#(error …)`) test (exact).
- **D-2 → open:** assert a **non-empty `path`** pointing at the failing field (e.g.
  `[tracking]` / `[shipped,tracking]`) for a bad nested field. (Until tested, the path code
  is unexercised and may be wrong.)
- **D-3 → open (demo):** the graceful-decode core is done, but the web-input demo must
  decode a *realistic structured* input (a tagged tuple / map with fields), valid → ok and
  **wrong-field** → error — not just `pending`/`42`.
- **D-7 → open:** add enum + transparent validator CT (exact). Don't assume backend-identical.

**Legitimately deferred → M4.6:** D-5 (render helper), D-6 (map standardization) — display
polish, pre-authorized split. Fine.

**Trend:** this is the same "code present, defining capability untested, marked done(-caveat)"
pattern (M1-5, M2-9, M3, C-4, M4-2-as-first-cut) — now on M4.5's *headline* capability. CC
is honestly *disclosing* the gaps (good), but still labeling them `done(caveat)` instead of
`open`/`deferred`. The cheap fix (a with-fields fixture + bad-field + path + enum/transparent
tests) is exactly what proves the milestone did its job.

## Closure

**Not yet closed (CDC).** The membrane's graceful-vs-crash *behavior* (D-3/D-4) is real and
proven — but M4.5's distinguishing capability (deep field validation, path-at-depth, nested,
enum/transparent) is **untested**: every fixture is nullary/top-level, which M4's shallow
guards already cover. Blocking clean close: D-1 (with-fields + bad-field), D-2 (non-empty
path), D-3 (realistic with-fields web-input demo), D-7 (enum/transparent validator CT) —
all cheap, mostly test-writing against existing validator code. D-5/D-6 stay deferred to
M4.6. Tally: Done 2 (D-4, D-8) · Open 4 (D-1, D-2, D-3, D-7) · Deferred 2 (D-5, D-6 → M4.6).
